1. **障碍格与贴纸可以相邻**：文档规定留白只约束“不同贴纸之间”，障碍格（邮票/胶带）非贴纸，故按可相邻实现。若希望障碍格也留白，改 `validator.js` 一处即可。
2. **关卡 1–3 定位为入门**（文档：入门 = 多种解法）：三关解法数均 > 20000，难度靠贴纸数量与形状复杂度递进（占用格 12 → 22 → 31，密度 33% → 45% → 48%）。第 3 关如需更紧的解法数（5–15），可加贴纸或缩板，重新跑 verify 即可。
3. **关卡数据用 JS 而非 JSON 文件**：保证 file:// 双击可运行（fetch 在 file:// 下受 CORS 限制）。三层数据结构与文档 9.1 的 JSON 示例一一对应。
4. **正式关卡 1–3 旋转名额为 0**（按 50 关规划，16–20 关才引入旋转）；旋转能力引擎已完整实现并用“🧪 旋转测试关”（页脚入口，2 个名额 + 3 杯同款咖啡）验证。

## 补丁 2026-11-02（二）："看起来占的格 ≠ 实际占的格"——占位格可视化

### 用户反馈（第二轮）

用户准确指出：**贴纸像素画看起来占据的格子与判定实际占据的格子不一致**，例证是第 2 关左上角 90° 方向的小雏菊：逻辑占 (0,0),(1,0),(1,1) 三格，但画面上花头只占右列两格，(0,0) 里只有一根细茎——看着空着，实际整格被占，周围的空位因此被留白规则封死。

### 根因

判定按**整格**算（需求 §2.3），美术是 die-cut 风格**像素画**，不必填满格子。两者本来就允许有偏差（美术/逻辑分离是需求的设计），但偏差大时没有任何可视化，玩家无从知道真实占位——花朵最严重（茎只有 4/8 像素宽，占位格约 25% 视觉覆盖）。

### 修复：让"实际占据"看得见（三层）

| 层 | 做法 |
|---|---|
| 交互可视化 | 新增 `Renderer._drawCellFootprint`：拖拽幽灵按占位格画绿/红半透明圆角块（叠在贴纸下）；非法落点闪烁红色块；挡路贴纸按占位格标红；**点击选中**任意贴纸显示淡粉占位格（点一下就知道它占哪几格）；**托盘**里每张贴纸下面画浅粉占位格（拿起前看清形状） |
| 美术修正 | 重画小雏菊：大花盘铺满上两格 + 带叶脉的叶子填满左下格，视觉覆盖 ≈ 逻辑占位（其余贴纸覆盖良好，未改） |
| 回归防线 | verify.html 新增"美术像素必须落在形状占位格内（且每个占位格非空）"检查，7 种贴纸全过——以后任何美术改动若与形状错位会直接报错 |

### 验证

- verify.html：43 项检查全部通过（+7 项美术对齐）；
- **像素级采样验证**（stub 贴纸精灵后 `getImageData` 逐点采样画布）：选中淡粉、托盘色块 #f6e7ee、合法幽灵绿、非法幽灵红、挡路贴纸红、闪烁红，全部在预期格子中心测得预期颜色；非占位格无色块；
- 拖拽/落点交互链路复测通过；控制台无错误；用户存档（已通第 2 关、解锁第 3 关）完好。

### 备注

排查中一度怀疑"通关后 completed 标记未持久化导致已胜利布局被恢复、输入锁死"，核实为**测试脚本自身引用了旧的 Game 对象**（`dbg.game` 在 `loadLevel` 前取值）——游戏无此 bug，存档的 completed/unlocked 均正确。

## 补丁 2026-11-03（三）：真正的根因——精灵渲染从未旋转（用户二次实测发现）

### 诊断修正

补丁（二）的结论不完整：占位格错位的主因**不是**"die-cut 像素画不满格"，而是 **`Art.getSprite` 存在渲染 bug**：它用 `rowsFor(artKey, 0)` 生成精灵（永远画未旋转的底图），`rotation` 参数只进了缓存键、从未参与绘制。后果：

- 所有带初始方向的贴纸**画面保持 0° 形态、逻辑却在转**：第 2 关叶子（画面横躺、逻辑竖直两格）、第 2/3 关小雏菊、第 3 关杯子蛋糕/咖啡同理；
- 旋转功能的**视觉表现从未生效**（测试关旋转后画面不变、占位却变了）。

用户以"绿草叶子逻辑占格应是左右而非上下"准确指出错位，并坚持"目标是视觉占格与逻辑占格最终一致，不能只把逻辑占格显示出来"——完全正确。

### 修复

| 位置 | 变更 |
|---|---|
| `js/ui/art.js` | `getSprite` 改用 `rowsFor(artKey, rotation)` 真正按方向生成精灵；`getTinted` 缓存键按 steps 归一化 |
| `tools/verify.html` | 新增"精灵各方向尺寸 = 旋转后形状包围盒"检查（7 贴纸 × 4 方向）——**渲染层此前零测试覆盖**，此检查杜绝"贴图未随逻辑旋转"这类 bug 复发 |

修复后**无需**改关卡数据（把某关叶子逻辑从竖改横）或重画美术：美术本来就带 4 个旋转形态，渲染正确后视觉与逻辑自动一致。补丁（二）的占位格可视化（幽灵/闪烁/挡路/选中/托盘色块）与小雏菊重画保留，但定位从"弥补错位"变为"交互反馈增强"。

### 验证

- verify.html：**50 项检查全部通过**（+7 项精灵旋转尺寸检查）；
- 像素级终验：`leaf@90` 精灵 64×128（修复前 128×64）；叶子放 (3,3) 后采样——(3,3)/(3,4) 格中心为叶子绿 `(111,191,115)`，右侧 (4,3)/(4,4) 为纸色，即**精确渲染在竖直逻辑两格内**；
- 旋转沙盒：咖啡旋转后精灵 192×128 → 128×192，旋转首次"看得见"；
- 控制台无错误；用户存档完好（已通第 2 关、第 3 关解锁）。

### 教训（记录给后续里程碑）

1. 两次用户截图都指向**渲染层**，而既有自动化测试（单元/求解器/交互）全在**逻辑层**——"判定对"不等于"画面对"。渲染层检查（精灵尺寸/采样）已纳入 verify.html；
2. 排查视觉问题时，测试应直接测**实际渲染产物**（getSprite/getImageData），而不是测 rowsFor 等中间函数——补丁（二）正是验错了层才误诊。

## 补丁 2026-11-03（四）：全量自检 28 组零错位 + 对齐检查升级为永久门禁

### 用户反馈（第三轮）

第 3 关咖啡杯再次被报告错位；用户指令：**全部自检现有素材，之后生成的新素材（含 M4 PNG）也一律严格检查错位**。

### 全量自检方法与结果（0 错位）

- **28 组全检**：7 种贴纸 × 4 方向（0/90/180/270），用 `Art.rowsFor(art, rot)`（getSprite 的真实绘制源）算出"像素实际落在哪些格"，与 `Geometry.cellsAtRotation` 的"逻辑占哪些格"逐组比对。判定标准两条：像素不得画出逻辑格外；每个逻辑格内必须有像素。**28/28 通过，0 项违反**。
- **第 3 关实测**（排除"单测过、实机不过"）：实际加载第 3 关，放置初始 90° 的咖啡杯于 (2,2) 后对棋盘 `getImageData` 逐格采样：5 个逻辑格 (2,2)(3,2)(2,3)(3,3)(3,4) 全部为杯身奶白 `(255,246,233)`；逻辑空格 (2,4) 与右侧邻格 (4,2) 均为纸色 `(255,253,247)`——画面占格与逻辑占格完全一致。

### 结论：无残留 bug，用户观察大概率来自未刷新的旧页面

补丁（三）修复 `getSprite` 前的旧代码把**所有**带初始方向的贴纸画成 0° 形态（逻辑却在转），第 3 关咖啡杯 90° 正是重灾区——修复后若页面未硬刷新，看到的仍是旧渲染。已请用户硬刷新（Ctrl+F5）复核；若仍见错位，报告具体位置即可复现排查。

### 永久门禁（用户指令落地）

### 验证

- verify.html：**50 项检查全部通过**（对齐检查 7 项 × 各 4 方向），4 关全部可解；
- 游戏页硬刷新后存档完好（已通第 1/2 关、第 3 关解锁、无第 3 关布局），控制台无错误。

## 补丁 2026-11-03（五）：提示去重——同一布局下看过的提示不再重复出现

### 用户需求

玩家在某提示后**没有做任何操作**又点了提示，新提示必须和上一条不同（同一布局下所有已展示过的提示都不再重复）；布局一变化，去重记录作废。

### 设计

三个关键决定：

1. **"布局相同"用存档签名判定**：`JSON.stringify(game.serialize())`（位置/方向/能力/名额全量）。选中贴纸不改签名（不算操作），放置/放回/旋转/解锁都改。
2. **去重 key 按"用户可见内容"生成**（`HintManager.contentKey`），而不是内部结构：
   - Hint 1 = 贴纸 + 占位格（`1:pid:cellsKey`）——同一张贴纸的不同位置算不同提示；
   - Hint 2 = 贴纸（`2:pid`）；Hint 3 = 结果（`3:ok`）；
   - Hint 1 死局与 Hint 3 失败**文案/视觉完全相同**，统一记 `layout:dead`；
   - 超时/错误返回 `null` 不参与去重（重试是自然操作）。
3. **seen 由调用方维护、按约定传递**：main.js 持有 `hintSig + hintSeen[]`，布局签名一致才传 seen；换关/重置清空。hints.js 信任该约定不自行校验（职责分离）。

### 实现要点

| 文件 | 变更 |
|---|---|
| `js/core/hints.js` | `contentKey`；`getHint` 类型随机后逐个尝试、结果命中 seen 就顺延换类型、全重复 → `{type:0, reason:"exhausted"}`；`hint1` 优先挑没展示过的建议，参考解全看过时 `_freshPlacement` 枚举其他合法位置（**锁定后仍可完成才算数**，仍属于完整可行解）；`hint2` 跳过已展示贴纸（布局未变 ⇒ 仍可行，无需重解），只剩已看过的就原样返回供换类型 |
| `js/main.js` | `hintSeen`/`hintSig` 状态；点提示时比对签名决定是否传 seen；记录新 key（超时/错误不记）；exhausted 文案「这个布局的提示都出现过啦——动一动贴纸，再来要新提示吧~」；换关重置记录 |

### 验证

- `tools/verify.html`：**62 项检查全部通过**（+3 项去重专项：Hint2 去重行为；同布局连续提示不重复→恰好 3 种→exhausted→布局变化重置；Hint1 为同一贴纸给出没看过的其他可行位置且该位置锁定后仍可完成）；
- **真实页面端到端**（旋转测试关，放置 1 张贴纸后真实随机连点 6 次 💡）：返回 **6 条互不重复**的提示——`2:berry_01`、`3:ok`、`1:berry_02:4,3`、`1:coffee_01:...`、`1:coffee_02:...`、`1:coffee_03:...`（4 条 Hint1 为不同贴纸/不同位置，替代位置搜索生效），无 exhausted 误触发；把贴纸放回托盘（布局变化）后再点 → 恢复正常提示；
- 控制台 0 错误/警告；用户存档完好（第 1/2/3 关全部通关，通关布局已保存）。

### 教训

- 求解器是**决定论**的：同一布局永远给出同一个参考解，所以 Hint 1 的多样性必须靠显式的"替代位置搜索"（枚举合法位置 → 逐个锁定后求解验证），而不能指望重跑求解器换结果；
- 去重 key 若按内部结构（如 solve 返回的摆放 id）生成，会出现"玩家看着一样、系统认为不一样"的假阴性——**key 必须对齐用户可见内容**。
